# Guest update offer compatibility

The update API requires a caller-generated `request_id` and one to 32 canonical UUIDs. The request identity binds permanently to the sorted target set. Replays inspect retained status; they do not issue another download URL. Duplicate, unknown or ambiguous targets, conflicting identities and targets already present in any retained request are refused.

The version 1 `guest_update_state` ledger records queued targets and `offered_unconfirmed` targets. The server persists the latter before returning a URL. This means a lost response may leave a retained offer without a guest receiving it. Telemetry and version strings are not installation acknowledgements. The status explicitly reports that guest effects are unverified.

Only admissions durably acknowledged in the current process can issue an offer. Every recovered queued target is fenced, including one restored from a stale backup. Replaying its request cannot grant ownership. A save failure also fences delivery and backup export. There is no automatic reset, pruning, TTL, replay, or new request for the same retained target. Other targets remain eligible. The ledger is bounded to 256 requests, 32 targets per request and 1 MiB compact JSON; capacity refusal preserves existing records. Explicit linux/windows amd64 telemetry is required; unsupported or missing platform information does not consume a queued target.

JSON and Mongo persistence, fresh destination restoration and backend migration retain and compare the complete ledger. Unsupported versions, fields, aliases, types, phases and Mongo indexes are refused. Cached Mongo backup export checks persisted barriers before serializing state. This is single-writer server accounting, not coordination between external writers or a backup guarantee for writes made after a snapshot.

Synthetic tests exercise validation, concurrent offers, retries, persistence failures, restart, backup and fresh restore, including stale queued restoration. Native application acceptance uses synthetic telemetry and does not fetch or execute a guest binary. It does not prove installation, guest acknowledgement, guest grow operations, native effects, or full legacy compatibility. Older guests without explicit platform fields cannot receive an update offer through this path. Pinned old-writer rollback after new writes remains unqualified; preserve original legacy data and raw history indefinitely. UI execution, releases and deployment remain on hold.
