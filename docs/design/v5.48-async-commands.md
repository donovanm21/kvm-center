# v5.48 — Bullet-proof agent commands: durability, real-time, and graceful long-running ops

**Status:** approved (open questions resolved 2026-04-30), ready to implement
**Owner:** kvm-center
**Target releases:** v5.47.2 (Phase 1), v5.48.0 (Phase 2), v5.48.1 (Phase 3)

## Goals

The operator experience must remain **near-identical to today's real-time
feel** for fast actions (sub-second feedback for START / STOP / RESTART)
while gaining **intelligence around long-running actions** — and the agent
must be **bullet-proof in durability** against every realistic edge case:

- Agent process restart mid-operation
- Agent host reboot (kernel panic, power loss) mid-operation
- Server restart while operations are in flight
- Network partition between server and agent during an operation
- Stuck `virsh` / `qemu-img` / external child process that never exits
- An operator triggering the same action twice in quick succession
- Storage exhaustion mid-operation (`/tmp` full while qemu-img writes)
- Agent's local journal / state file corrupted by a crash
- Multiple operators reaching for cancel simultaneously
- A long-running operation that *succeeds* while the operator is
  disconnected — they should see the success when they reconnect

The current architecture fails most of these: tonight's `DELETE_SNAPSHOT`
divergence and the live `MIGRATE` stuck-at-99% record both happened during
*normal* operation. Adding hostile inputs (reboots, partitions) makes the
gap wider.

## Problem evidence

The 2026-04-30 hvnode01 thermal-trip incident produced three concrete
failures, all rooted in the same architectural gap:

| Symptom | Surface | Root cause |
|---|---|---|
| `DELETE_SNAPSHOT` returned `{"success":null,"message":""}`; record marked failed | `/api/admin/command-log` shows `outcome=failed`, but `virsh snapshot-list Docker` confirms the snapshot was actually deleted | qemu-img commit on a 24 GiB internal snapshot took longer than the server's HTTP-client timeout. Server gave up. Agent finished. State diverged. |
| Live `MIGRATE` API call expired at 1200 s | kvm-center record stuck at `phase=transfer pct=18` for hours, then `status=failed` even though libvirt was actively progressing through 99% | server's blocking call timed out while libvirt's pre-copy convergence loop kept iterating |
| Operator UI showed migration `failed` while it was actually still running | SPA `/migrations` page | downstream of the same root cause — the server's record is the SPA's source of truth |

The pattern: **the server's HTTP request to the agent is the operation's
single source of truth**. Anything that exceeds that one request's
lifetime drops bookkeeping. Restarts, partitions, and stuck processes
make this worse.

## Existing substrate (don't re-derive)

v5.32.17 already shipped most of the infrastructure we need:

- Every mutating `/api/command` carries (or is assigned) a `request_id`.
- Server records `{request_id, action, target, params, submitted_at}` to
  `command_log` **before** dispatch. Persists in Mongo / JSON.
- Agent maintains a 10-minute outcome cache keyed on `request_id`.
- Boot reconciler walks `command_log` entries with `outcome=pending` >
  45 min, marks them `unknown`.
- v5.32.21 added `/api/admin/reconcile/{host}` for on-demand divergence
  surfacing.

What's missing for "bullet-proof": durability of the agent's own state,
liveness tracking, watchdog control over child processes, real-time
progress streaming for slow actions, and cancellation.

## Architectural building blocks

Six pieces, all of which must work together. None on its own makes the
agent bullet-proof; the combination does.

### 1. Persistent agent state (`/var/lib/kvm-center/operations.db`)

The agent's outcome cache is in-memory today (lost on restart). For
durability we move it to a **SQLite** database on disk (industry-standard
for embedded persistence; pure-Go driver via `modernc.org/sqlite` so we
keep the agent CGO-free).

**Every action is persisted, not just slow ones** — for forensics and
operator-experience consistency. Fast actions (START / STOP / RESTART)
skip the watchdog/heartbeat goroutines but their lifecycle row still
lands in the DB. This means the Recent Tasks pane shows the full picture
of fleet activity, not a subset, and an operator can audit "what
happened on hvnode02 last Tuesday" against a single timeline.

Schema:

```sql
CREATE TABLE operations (
  request_id        TEXT PRIMARY KEY,
  action            TEXT NOT NULL,
  vm_uuid           TEXT,
  vm_name           TEXT,
  params_json       TEXT,
  state             TEXT NOT NULL,    -- pending | running | success | failed | cancelled | unknown
  submitted_at      INTEGER NOT NULL, -- unix ns
  started_at        INTEGER,
  last_heartbeat_at INTEGER,
  completed_at      INTEGER,
  output            TEXT,
  error             TEXT,
  child_pid         INTEGER,           -- the virsh / qemu-img PID, if any
  watchdog_at       INTEGER             -- when to kill if still running
);
CREATE INDEX ops_state ON operations(state);
CREATE INDEX ops_heartbeat ON operations(last_heartbeat_at);
```

SQLite is file-backed, journal-mode WAL, sync NORMAL. Survives agent
restart; survives host reboot (it's persisted on the host's disk, not
in the kvm-center-agent process). Database file is ~100 KB even after
years of operation; we keep terminal entries 7 days for forensics, then
GC.

### 2. Watchdog with controllable timeouts

Every operation gets a per-action watchdog timeout, set when the operation
is registered. Defaults:

| Action | Watchdog | Rationale |
|---|---|---|
| START / STOP / RESTART / FORCESTOP | 60 s | Should be sub-second; 60 s catches a wedged libvirtd. |
| POWER_CYCLE | 90 s | Shutdown + start; ACPI shutdown can take ~30 s. |
| CREATE_SNAPSHOT | 5 min | qcow2 snapshot is metadata-only; 5 min is huge headroom. |
| DELETE_SNAPSHOT | 30 min | qemu-img commit can be slow on big VMs. |
| REVERT_SNAPSHOT | 5 min | Rare slow case. |
| MIGRATE (live) | 60 min | Includes convergence loop; longer than today's 30 min. |
| OFFLINE_MIGRATE | 90 min | Includes disk transfer; huge VMs need headroom. |
| EDIT_VM (no shutdown) | 30 s | Pure XML edit. |
| EDIT_VM (allow_shutdown) | 5 min | Includes ACPI shutdown + restart. |

Watchdog enforcement: when the watchdog fires, the agent SIGTERMs the
child PID, waits 5 s, SIGKILLs if needed. Marks the operation `failed`
with `error="watchdog: action did not complete within Ns"`. This covers
"stuck virsh", "stuck qemu-img", any external process hanging on a
broken kernel.

Operator override: the API accepts a `watchdog_seconds` param to
override per-call. Useful for huge offline migrations on slow links.

### 3. Heartbeat — proof of life for in-flight operations

Every running operation refreshes its `last_heartbeat_at` in the
operations DB every 30 s. When the agent starts (or restarts), it scans
for operations in `running` state and:

- If `last_heartbeat_at` is fresher than 90 s and the recorded `child_pid`
  exists → operation is genuinely in flight; reattach the watchdog.
- If `last_heartbeat_at` is stale OR `child_pid` is gone → operation is
  abandoned (agent crashed or was killed mid-op). Run **boot
  reconciliation** (block 5).

The server-side reconciler's polling logic uses the heartbeat as well:
it can detect "agent went silent on this operation" without waiting for
the watchdog timeout.

### 4. Cancellation

Operator can cancel any running operation:

```
POST /api/command/cancel?request_id=<id>&reason=<text>
```

Server records `cancellation_requested_at`, calls agent's
`POST /command/cancel?request_id=<id>`. Agent SIGTERMs the child PID,
waits 5 s, SIGKILLs if needed, marks operation `cancelled` with the
operator's reason.

For migrations, this is `virsh domjobabort <vm>` rather than killing the
virsh process — cleaner cancellation. The dispatch layer knows which
cancel mechanism each action uses.

### 5. Boot reconciliation on the agent

When the agent starts (cold boot or restart), it scans
`/var/lib/kvm-center/operations.db` for entries in `pending` or `running`
state. For each one, it asks libvirt: did the operation actually
complete while we were down?

Logic per action:

| Action | Reconciliation |
|---|---|
| START | If VM state is `running` → `success`. Else → `unknown`; report and let server's reconciler decide. |
| STOP / FORCESTOP | If VM state is `shut off` → `success`. Else → `unknown`. |
| CREATE_SNAPSHOT | If snapshot with target name exists → `success`. Else → `unknown`. |
| DELETE_SNAPSHOT | If snapshot with target name does NOT exist → `success`. (This is exactly what saved us tonight on hvnode01.) |
| MIGRATE / OFFLINE_MIGRATE | If VM is now defined on dest and not on source → `success`. If on source but not dest → `failed` (rollback case). Else → `unknown`. |
| REVERT_SNAPSHOT | Inspect VM state + current snapshot; cross-reference. |
| EDIT_VM | Compare current XML to expected post-edit XML. |

After reconciliation, every entry is in a terminal state (or
`unknown`). The agent posts the reconciled outcomes to the server in
batch on its first telemetry tick.

### 6. Real-time progress streaming for long-running actions

Today's gRPC `StreamMigrationProgress` pattern works. Extend it: every
async action emits progress frames over a single agent → server gRPC
stream `StreamCommandProgress`:

```protobuf
message CommandProgressFrame {
  string request_id = 1;
  string phase = 2;        // human-readable; e.g. "shutting down VM"
  int32 progress_pct = 3;  // 0-100, or -1 for indeterminate
  string detail = 4;
  string error = 5;        // populated only on terminal failure
}
```

Frames are emitted at:
- Every state transition (`pending → running → terminal`)
- Every 5 s during a running operation that supports progress reporting
- The action wrapper handles emitting; individual actions just call
  `progress.Update(pct, detail)`

Server fans out frames via SSE to connected SPA sessions — exactly the
mechanism the migration progress bar already uses today. Operator
disconnects during a long op? Server still receives frames, persists
them in `command_log`, and sends the latest state to the SPA on next
reconnect. **No state lost just because the operator's tab was
backgrounded.**

## State machine

Every operation passes through this state machine. Every transition is
durable (persisted to operations.db on agent and command_log on server)
and observable (audit + SSE event).

```
                     +-------+
  POST /command  --> |pending|       (registered, dispatched)
                     +---+---+
                         |
            agent starts the work
                         |
                         v
                     +-------+
                     |running|  --+  heartbeat every 30 s; watchdog ticks
                     +---+---+   |
                         |       |  watchdog expired
                         |       +-----> SIGTERM/SIGKILL child --> failed
                         |
                         |  /command/cancel received
                         |       +-----> SIGTERM/SIGKILL child --> cancelled
                         |
                         |  agent crashes / restarts mid-op
                         |       +-----> on next start, boot-reconcile
                         |                  child_pid gone + libvirt confirms outcome
                         |                  -> success | failed | unknown
                         |
                         |  child exits cleanly with success
                         v
                     +-------+
                     |success|
                     +-------+

  Any state where reconciliation can't determine truth -> unknown.
  unknown is operator-actionable; admin reconcile endpoint can refresh.
```

## Failure-mode matrix

The bullet-proof claim must hold against this matrix.

| Failure | Today | After v5.48 |
|---|---|---|
| Server HTTP timeout to agent (operation succeeds anyway) | Bookkeeping diverges; record `failed` | Phase 1 reconciler salvages → `success` |
| Server crashes after dispatching but before recording outcome | command_log entry stuck `pending`; manual reconcile required | command_log fsynced before dispatch (already); on server boot, `command_reconciler` polls every pending entry's agent → resolves to terminal state |
| Agent crashes mid-operation; child process killed by parent death signal | Operation lost; libvirt may have done partial work | Persistent ops.db + boot reconciliation; libvirt reality is the truth, agent surfaces it |
| Agent crashes mid-operation; child process orphaned but continues (`PR_SET_PDEATHSIG` not set, child reparented to init) | Operation may continue; agent is unaware on restart | On agent start, scan ops.db; if `child_pid` still alive in `/proc`, re-attach the watchdog; if child completed and exited, query libvirt for outcome |
| Agent host reboots mid-operation | Same as agent crash, but child is also gone | Boot reconciliation; libvirt-reality lookup |
| Network partition between server and agent during long op | Server marks failed; bookkeeping diverges on heal | Phase 1 reconciler retries through partition heals; agent's persisted outcome wins |
| Stuck `virsh migrate` (e.g. hung on iblock) | Operation hangs forever; operator has no recourse | Watchdog SIGKILLs after action's timeout; operator can also cancel |
| `qemu-img convert` fills /tmp | Operation fails at disk I/O; agent reports failure | Watchdog still applies; failure is reported promptly with error context. Agent also pre-flights free space before starting (defence in depth) |
| Operator double-submits same `request_id` | Idempotency cache returns first outcome | Same; cache now persistent so it survives across restarts up to 7-day retention |
| Operator double-submits *different* `request_id` for same logical action (e.g. delete same snapshot twice) | Both attempted; second usually fails because the work is already done | Phase 2 dispatch can detect "operation already in flight on this VM" and reject second with 409 (preserves operator intent rather than racing) |
| Server boots fresh against an agent that has running operations | command_log on server doesn't know about them | Agent's first telemetry tick after server reconnect includes a "recovered ops" summary; server adopts them into command_log |
| Agent's ops.db corrupted | N/A (no DB today) | On open failure: rebuild from scratch (lose history); agent logs critical, alerts operator. All in-flight ops lost; rely on libvirt reality for current truth |
| Operator UI session disconnects mid-progress | They miss the update | SSE replay on reconnect: server includes last-known progress for all running ops; SPA shows live state immediately |
| Two cancels racing | First wins, second is no-op | Second sees state=cancelled, returns 200 + idempotent message |

## Phased rollout

### Phase 1 — Server-side reconciliation + agent outcome read endpoint (v5.47.2)

Salvages tonight's failure mode without breaking compatibility.

**Server changes:**
- `command_log` entries gain `inflight_until`, `last_polled_at`,
  `last_heartbeat_at` columns (additive).
- Server's HTTP failure branch marks `pending` (not `failed`) on timeout
  / transport error. Real 4xx from agent still marks `failed`.
- New goroutine `command_reconciler` polls `pending` entries via
  `GET /command-outcome?request_id=…` on the agent. Updates outcome
  on terminal response. SSE-fanout the transition.
- Server boot path: on startup, walks `command_log` for pre-restart
  pending entries and primes the reconciler with them.

**Agent changes:**
- New endpoint `GET /command-outcome?request_id=<id>` reads the existing
  in-memory outcome cache. Returns 404 if unknown.
- (No persistent state yet; that's Phase 2.)

**Observability:**
- Audit event `command.reconciled` on each transition. Includes how long
  after `submitted_at` the resolution arrived.
- Metric counter for `pending → success` transitions resolved by
  reconciler vs. timeout.

**Effort:** ~2 days.

**Risk:** low. Pre-Phase-1 agents return 404 to the new GET; reconciler
treats that as "unknown, fall back to v5.32.17 timing".

### Phase 2 — Persistent agent state + watchdog + async-by-default + cancellation (v5.48.0)

The bulk of the bullet-proofing.

**Agent changes:**
- New `operations.db` (SQLite) at `/var/lib/kvm-center/operations.db`.
- Action dispatcher rewritten: every action declares `async: bool`,
  `watchdog: time.Duration`, `progress_supported: bool`, and
  `cancel_method: enum`.
- Slow actions (`DELETE_SNAPSHOT`, `MIGRATE`, `OFFLINE_MIGRATE`, etc.)
  return `202 Accepted {"request_id":…}` within 100 ms.
- Goroutine wrapper: persists `running` state, registers child PID,
  spawns watchdog, runs action body, persists terminal state on exit.
- Heartbeat goroutine: refreshes `last_heartbeat_at` every 30 s.
- Boot reconciliation: on agent startup, scans operations.db, queries
  libvirt for in-flight ops, updates state to terminal or `unknown`.
- New endpoint `POST /command/cancel?request_id=<id>` — sends cancel
  signal to the running goroutine. SIGTERM child → wait 5 s → SIGKILL.

**Server changes:**
- Handles `202 Accepted` from agents (treats same as `pending` for
  command_log purposes).
- New `POST /api/command/cancel?request_id=<id>` proxies to agent's
  cancel endpoint.
- gRPC `StreamCommandProgress` registered on agent service. Frames flow
  for *all* slow actions, not just migrations.

**SPA changes:**
- Migration progress bar generalised to a "command-in-flight" banner that
  works for any slow action.
- Cancel button on running ops where supported.

**Effort:** ~5 days (3 agent, 1 server, 1 SPA + integration tests).

**Risk:** medium. Agent dispatcher refactor touches every action; needs
strong test coverage. Wire-shape change (`200` → `202`) is gated by a
feature flag for staged rollout.

### Phase 3 — Real-time gRPC progress for all actions + UX polish (v5.48.1)

Everything has a state machine but slow actions still feel sluggish in
the SPA without progress detail. Phase 3 brings real-time UX.

**Agent changes:**
- `progress.Update(pct, detail)` wrapper available to every action body.
- Migration code (already streams) generalised; other slow actions add
  progress hooks where they can (e.g. qemu-img convert can parse stderr;
  qcow2 commit can use libvirt block-job-info).

**Server changes:**
- SSE channel emits `command_progress` events; SPA subscribes per
  visible operation.
- On SPA reconnect, server replays last-known progress frame from
  command_log.

**SPA changes:**
- Per-operation progress widget with phase + percentage + detail.
- "Recently completed" notifications surface even if the operator was
  away when it happened (uses persistent operations history).

**Effort:** ~3 days.

**Risk:** low. Building on Phase 2's foundations.

## Migration & backward compat

- **v5.46 server / v5.47.2 server with v5.46 agents**: Phase 1's GET
  endpoint returns 404 on old agents → reconciler treats as fall-through
  to today's timing. No worse than today.
- **v5.48.0 server with v5.47.x agents**: server expects 202 from new
  agents on slow actions. Old agents still return 200 sync; server
  treats both correctly. Detection: agent advertises capabilities on
  telemetry payload (`agent_caps: ["async_commands_v1"]`).
- **v5.48.0 agents with v5.46 server**: agent returns 200 sync regardless
  of capabilities (matches what server expects). Fleet rollout-safe in
  any order.

Feature flag `Features.AgentAsyncCommands` (default: on) lets the operator
disable per-cluster if needed during rollout. Server falls back to sync
behaviour when off.

## Decisions log

Resolved during 2026-04-30 design review:

1. **Persistent store: SQLite** (industry-standard for embedded
   persistence). Pure-Go driver `modernc.org/sqlite` keeps the agent
   CGO-free. WAL journal mode, NORMAL sync.

2. **Capture every action, not just slow ones.** All actions persist
   to `operations.db` for consistency and forensics. Recent Tasks pane
   shows the full picture; auditing is single-source. Fast actions
   skip the watchdog/heartbeat goroutines but get the same DB lifecycle.

3. **Notifications: failures notify by default, successes opt-in.** Any
   task ending in `failed`, `cancelled`, or `unknown` fires a
   notification on the deployment-default channel — not configurable
   off (operators always want to know something failed). Success
   notifications are opt-in per-operator via Settings → Notifications →
   My tasks, with per-action granularity. Gated by
   `Features.NotifyOnTaskFailure` flag (default: on).

## Standing notes

- **Operations queued during a server outage.** Agent has no concept of
  a server-side queue; operator's API request fails immediately if
  server is down. Server's `command_log` only records ops after the
  operator's request is accepted. ✓ (no design change needed)

- **Server-side equivalent of agent's boot reconciliation.** On startup,
  walk `command_log` for pre-restart pending entries and prime the
  reconciler. Already in Phase 1's scope; mentioned here for emphasis.

- **Cancellation for fast actions.** Op completes faster than the cancel
  round-trip; cancel only exposed on slow actions. Fast ones return
  `409 Conflict` if cancellation is requested.

- **Multi-agent operations** (migration involves source + destination).
  Source agent is authoritative; destination is a passive participant.
  Phase 2 keeps this — watchdog/cancellation applies on source, source
  coordinates dest.

- **kvm-tools (in-guest daemon)** is **out of scope** for this design.
  Guest commands are short-lived (telemetry-only) and don't exhibit the
  long-running pattern this spec targets.

## vSphere-parity UX (Phase 3 scope expansion)

The architecture above is the *substrate*; this section is the operator
experience built on top of it. Target: a vSphere/vCenter user can sit
down at kvm-center and feel at home.

### The "Task" abstraction

Every mutating action — `POST /api/command`, `POST /api/admin/restore`,
`POST /api/admin/grant-signer/rotate`, etc. — produces a **Task** that
the SPA tracks first-class. Tasks are the primary unit operators care
about. They have:

- **Name** (human-readable: "Delete snapshot snap-20260423-1301 on Docker")
- **Target** (VM / host / cluster — clickable to that object's page)
- **Initiator** (username or token name)
- **Submitted at / completed at / duration**
- **Status** (`queued | running | success | failed | cancelled | unknown`)
- **Progress** (% + phase + detail when reportable)
- **Output / error** (the verbose tail; one click to expand)

Tasks ARE the rows in `command_log` with a thin SPA-side wrapper. No new
backend abstraction; just a presentation layer.

### Recent Tasks pane (always visible)

Fixed-position pane at the bottom of every screen, mimicking vSphere's
Recent Tasks panel:

```
┌─ Recent Tasks ─────────────────────────────────────────────────────┐
│ ⏳ Delete snapshot 'pre-patch' on Docker     • alice • 00:42 •  ━━━━─── 67% │
│ ✓  Live migrate Docker → hvnode03            • alice • 03:21 • complete    │
│ ✗  Snapshot DRP                              • bob   • 00:08 • failed      │
│ ⏸  Restart VM1                               • alice • 00:01 • queued      │
└─────────────────────────────────────────────────────────────────────┘
                                           [collapse]   [show all (12)]
```

- Updates live via SSE (the existing `command_progress` channel).
- Survives navigation — same component, mounted at the Layout level.
- Click a row → modal with full task detail (output, error, phase log).
- "Show all" → `/tasks` page with full filterable history (today, last
  7 days, last 30 days; filter by status, target, initiator).
- Persists across browser refresh: the SPA fetches `/api/tasks/recent`
  on mount.

### Per-object task indicators

When a VM (or host) has an in-flight task targeting it, decorate it
in the inventory:

- **VMs list / Hosts list** — small spinning glyph next to the row
  with a tooltip showing the task name. Click → opens the task detail.
- **VM detail page** — banner at the top: "**Action in progress:**
  Delete snapshot 'pre-patch' (started 0:42 ago, 67%) — *Cancel*".
  When complete, banner flips to a transient "✓ Completed at HH:MM"
  notice that auto-fades after 10 s.
- **Host detail page** — same pattern. Shows the host-level task
  (maintenance enter, drain) plus a count of in-flight VM tasks on
  that host.

### Object-level locking

While a task is in flight on an object, the SPA disables conflicting
actions on that object:

- VM with `MIGRATE` in flight → `START`/`STOP`/`SNAPSHOT`/`DELETE_VM`
  buttons disabled (with hover tooltip: "Migration in progress").
- VM with `DELETE_SNAPSHOT` in flight → other snapshot ops disabled.
- VM with `EDIT_VM` (allow_shutdown) in flight → power actions disabled.

Server-side enforcement: the command dispatcher rejects with `409
Conflict` if a non-compatible task is in flight on the same target.
This means the lock is real, not just a UI hint — operators using
`kvmctl` or the API directly hit the same guard.

Compatible tasks (e.g. read-only ops, telemetry) pass freely.

### Auto-resume notifications

When an operator returns to the SPA after being away, surface tasks
that completed while they were gone:

- On login or tab refocus, the SPA queries
  `GET /api/tasks?initiator=me&since=<last_seen>`.
- If any tasks completed (success or failure), show a non-blocking
  banner: "While you were away: 3 tasks completed (1 failed). View"
- "View" expands the Recent Tasks pane filtered to this batch.
- Banner dismisses on click; subsequent visits don't replay.

This is the "I started a 30-min migration before lunch and want to
know how it went" flow.

### Task replay on session join

The SSE subscription on SPA load includes a "replay last N progress
frames" mechanism: server sends the most recent state of every task
the operator has permission to see, *before* live frames start. SPA
populates the Recent Tasks pane immediately — no flicker, no empty
state, no refetch round-trip.

For tasks that are still running, live frames take over from the last
replayed one without gaps.

### Cancel button

Every running task in the Recent Tasks pane gets a small × button
when:
- The action is cancellable (every slow action; not fast ones).
- The operator has permission for the action (the same RBAC perm
  that allowed the original action).

Click → confirm modal ("Cancel migration of Docker?") → POST
`/api/command/cancel`. Task transitions to `cancelled` within the
agent's response window (typically <2 s).

### Dashboard "fleet activity" widget

A homepage widget shows fleet-level task velocity:

- Tasks in last 24 h, by status (sparkline)
- Currently running tasks (numeric)
- Average task duration by action type

Helps operators spot anomalies: "we never had this many failed
DELETE_SNAPSHOTs before; something's up with hvnode02's storage".

### Task notifications via the existing channels

Phase 3 hooks the notifications subsystem (Discord/Slack/webhook,
already configured per-deployment) into terminal task transitions.

**Defaults:**

- **Failures always notify.** Any task that ends in `failed`,
  `cancelled` (operator-initiated), or `unknown` (reconciler couldn't
  determine outcome) fires a notification on the deployment-default
  channel. Cannot be disabled — the operator always wants to know
  something didn't work.
- **Successes are opt-in.** Operators who want positive confirmations
  enable them in Settings → Notifications → My tasks. Per-action
  granularity (e.g. "notify me on `MIGRATE` success but stay quiet on
  `RESTART` success").

This keeps the default volume low — operators who never touch settings
get exactly the signals they need, no more.

The `Features.NotifyOnTaskFailure` flag (default: on) gates the always-
notify behaviour. Cluster admins can flip it off if they're routing
failures through a different system entirely.

### What we deliberately don't bring from vSphere

- **DRS-style automated load balancing** — the homelab is small enough
  that manual decisions are fine; auto-rebalancing adds complexity for
  marginal benefit. Defer indefinitely.
- **Storage vMotion as a first-class concept** — kvm-center supports
  copy_storage already; surfacing it as a separate UI primitive
  duplicates work. Migrations imply storage move when the disks aren't
  shared.
- **Cluster-level resource pools** — out of scope; kvm-center's
  RBAC/group model already covers the homelab use case.
- **Customisation specs / templates** — VM templates are libvirt-side;
  kvm-center reuses them but doesn't manage them as first-class objects.

These are explicitly out of scope so we don't bloat the v5.48 surface.
They can be revisited individually if operator demand emerges.

## Why this is "bullet-proof"

The combination of:
1. **Persistent agent state** survives reboots/crashes.
2. **Watchdog** prevents stuck processes from hanging forever.
3. **Heartbeat** lets the server detect agent silence promptly.
4. **Cancellation** gives operators an escape hatch.
5. **Boot reconciliation** uses libvirt as ground truth on every restart.
6. **Real-time progress** keeps UX honest during long ops.

…makes the agent able to handle every entry in the failure-mode matrix.
The architecture's source of truth shifts from "the HTTP response" (today,
fragile) to "libvirt reality + persistent agent state, reconciled
continuously" (proposed, durable).

The operator never needs to know any of this is happening. From their
seat, fast actions stay sub-second, slow actions show real progress,
crashes self-heal on restart, and the SPA always reflects truth.
