# v5.48 implementation plan — autonomous execution checklist

**Spec:** `v5.48-async-commands.md` (PR #17)
**Status:** Phase 1 + 2 shipped (v5.47.2 + v5.48.0 deployed); Phase 3 in flight
**Next PR to ship:** **PR-3d** (see below)

This is a self-contained execution plan for the v5.48 work. Each PR is
small enough to fit a single focused session, lands behind a feature
flag where appropriate, and is independently mergeable. I can pick up
the next un-shipped PR at any time without further input — checkpoints
where I should *pause and ask* are explicitly called out.

## How to use this doc

When resuming work:
1. Re-read this file's "Next PR to ship" line at the top.
2. Open the matching PR section below.
3. Branch off `main` with the branch name listed.
4. Implement against the acceptance criteria.
5. Tests + lint must pass locally before push.
6. Open a PR via the Gitea API; wait for green CI; merge via API.
7. Update this file's "Next PR to ship" pointer + the row's status.
8. Stop if the next PR is marked **CHECKPOINT** — wait for operator input.

## Status legend

- ⬜ not started
- 🟡 branch open, in progress
- 🟢 merged to main
- 🚧 **CHECKPOINT** — pause for operator input before starting

## Definition of done (every PR, no exceptions)

Each PR is not "ready to merge" until **all four** are present:

1. **Code change** — implementation per the PR's scope.
2. **Tests** — at least the cases listed in the PR's acceptance criteria
   below. New unit tests for new functions; new integration tests for
   new endpoints / flows; new gRPC test for new RPCs. CI must pass
   green (`lint-test`, `webui-audit`, `gitleaks`, `e2e`).
3. **Docs** — at minimum:
   - Update `server/docs/` if the PR adds operator-visible behaviour
     (new endpoint, new UI surface, new failure mode the operator
     needs to recognise). New section in the right existing page or a
     new page if it stands alone.
   - Update `server/docs/api.md` for any new HTTP endpoint.
   - Update `server/docs/changelog.md` only on the **phase-final** PR
     (so the changelog entry summarises the whole phase, not 6 fragments).
   - Update this `v5.48-implementation-plan.md` — flip the row's
     status, advance the "Next PR to ship" pointer.
4. **Validation** — after merge, run the PR-specific smoke check
   listed in its "Validation" subsection below. For Phase 1 this is
   a one-liner; for Phase 2 / 3 it's typically a quick test against
   the demo stack or prod.

If any of the four is missing or fails, the PR is not done. Surface to
operator instead of merging on partial completion.

### 🟢 PR-1a — Mark pending, not failed, on HTTP timeout

**Branch:** `fix/v5.47.2-mark-pending-on-timeout`

**Scope:**

  cause is a transport error, `context.DeadlineExceeded`, or a 5xx from

  `InflightUntil` set, not `failed`.

- After window expires, entry transitions `pending → unknown`
  (not regression: same ultimate state today reaches via "failed").

**Test locally:**

### 🟢 PR-1c — Server reconciler goroutine

**Branch:** `feat/v5.47.2-command-reconciler`

**Scope:**
- `server/command_reconciler.go` (new): ticker-driven goroutine.
  Every 30 s, scans command_log for entries where:
  - `Outcome == "pending"`
  - `InflightUntil > time.Now()`
  - `time.Since(LastPolledAt) > pollInterval` (30 s)

  For each, calls `GET /command-outcome?request_id=...` on the target
  agent (via existing agent client; 5 s HTTP timeout). On terminal
  response, updates the command-log entry; on 404, leaves pending; on
  network error, leaves pending and bumps `LastPolledAt`.
- `server/main.go`: launch reconciler goroutine with `serverCtx`
  alongside other workers.
- SSE event `command_reconciled` fanned on each transition so the SPA
  refreshes affected migration-record badges.
- `server/audit.go`: new audit type `command.reconciled` for terminal
  transitions only (not per-poll, per the spec's open-question
  resolution).
- Integration tests:
  - `TestReconciler_RecoversFromHTTPTimeout` (full happy path).
  - `TestReconciler_AgentReturnsFailed` (propagates).
  - `TestReconciler_Agent404FallsBackToTimer` (pre-Phase-1 agent).
  - `TestReconciler_AgentUnreachable` (no spurious failures).

**Acceptance criteria:**
- All four integration tests pass.
- A live e2e test: stub agent that returns success after a 5 s delay
  combined with server timeout of 1 s — without reconciler, marked
  failed; with reconciler, marked success after ~30 s.
- Operationally: replays the `DELETE_SNAPSHOT` scenario from
  2026-04-30 (qemu-img commit takes longer than client timeout) and
  confirms command-log ends `success`, not `failed`.

**Docs (this is the phase-final PR for Phase 1):**
- `server/docs/changelog.md`: v5.47.2 entry covering 1a + 1b + 1c
  together — the operator-visible story is "long-running commands no
  longer show as failed when they actually succeeded".
- `server/docs/troubleshooting.md`: add a "Why a long-running action
  shows as `pending`" subsection explaining the reconciler's polling
  and the eventual `unknown` resolution.
- `server/docs/api.md`: document the new SSE event
  `command_reconciled` and its payload.

**Validation (post-merge, post-deploy):**
1. Run a real DELETE_SNAPSHOT on a VM with a non-trivial snapshot.
2. Watch `/api/admin/command-log?limit=5`. Confirm the entry
   transitions `pending → success` (not `pending → unknown` or
   `pending → failed`).
3. Confirm `command.reconciled` audit event fires.
4. If all three pass, tag v5.47.2 and proceed.

**Effort:** ~6 hours (includes integration tests).

**Risk:** low. Reconciler is additive; if it misbehaves, command-log
just gets noisier polls (idempotent).

### 🟢 PR-2d — Boot reconciliation + heartbeat

**Branch:** `feat/v5.48-agent-boot-reconcile`

**Scope:**
- Heartbeat goroutine refreshes `last_heartbeat_at` every 30 s for
  rows in `running` state.
- Agent startup path: scan ops.db for `running`-state rows. For each:
  1. If `child_pid` is alive in `/proc` AND heartbeat fresh (<90 s) →
     reattach watchdog (rare; agent restart without process death).
  2. Else → query libvirt for the action's expected post-state (per
     spec §5 reconciliation table) and mark the ops.db row terminal.
- New `agent/reconcile.go` with the per-action reconciliation logic.
- Reconciliation outcomes posted back to server via existing
  telemetry channel (server's command_log gets updated by the agent's
  next telemetry tick).

**Acceptance criteria:**
- `TestBootReconcile_DeletedSnapshotRecognised` — exactly tonight's
  scenario. Pre-populate ops.db with running DELETE_SNAPSHOT; ensure
  snapshot is gone in libvirt; restart agent; row → success.
- `TestBootReconcile_RunningProcessReattaches` — pre-populate with
  fresh heartbeat + live child PID; restart agent; watchdog re-attached.
- `TestBootReconcile_StaleEntryMarkedUnknown` — heartbeat stale,
  child gone, libvirt indeterminate; row → unknown.

**Docs:** new section in `server/docs/troubleshooting.md` —
"Agent restarted mid-operation: how the reconciler decides what
happened" — with the per-action reconciliation table from spec §5.

**Validation (post-merge):** on hvnode02 (lower-stakes), start a
CREATE_SNAPSHOT, immediately `systemctl restart kvm-center-agent`
mid-operation; confirm after restart the ops.db row resolves to a
terminal state (success if libvirt finished, unknown if interrupted).

**Effort:** ~6 hours.

**Risk:** medium — reconciliation logic is per-action; needs careful
coverage so a misclassification doesn't lie to operators.

### 🟢 PR-2e — Async dispatch for slow actions

**Branch:** `feat/v5.48-agent-async-dispatch`

**Scope:**
- Mark slow actions (DELETE_SNAPSHOT, CREATE_SNAPSHOT, MIGRATE,
  OFFLINE_MIGRATE, EDIT_VM+allow_shutdown) as `async=true` in the
  dispatcher table.
- Async actions return `202 Accepted {"request_id":…, "status":"running"}`
  within 100 ms of receipt, after persisting `running` state. Body
  runs in a goroutine.
- Server (`handlers.go:handleCommand`) recognises `202` and treats it
  same as `pending` for command_log purposes — reconciler from PR-1c
  takes over polling.
- Feature flag `Features.AgentAsyncCommands` gates this on the agent
  side. Agent advertises capability via `agent_caps` in telemetry; old
  servers see no `agent_caps`, treat agent as sync-only.

**Acceptance criteria:**
- `TestAsyncDispatch_DeleteSnapshotReturns202` — agent returns within
  100 ms; goroutine completes after delay; ops.db terminal.
- `TestServerHandles202` — server marks pending on 202, reconciler
  later transitions to terminal.
- `TestSyncFallback_FlagOff` — `AgentAsyncCommands=false` →
  agent returns `200` synchronously (back-compat path).

**Docs:** `server/docs/api.md` — note that slow actions now return
`202 Accepted` with `request_id` instead of synchronous `200 + output`.
Operator-facing snippet for `kvmctl` users showing how to read the
new shape.

**Validation (post-merge):** `Features.AgentAsyncCommands=true` on
prod, run a DELETE_SNAPSHOT, confirm:
- API call returns 202 within 100 ms (`time curl …` < 0.2 s).
- `/api/admin/command-log?limit=1` shows entry transition
  `pending → success` after the agent's actual work completes.

**Effort:** ~5 hours.

**Risk:** medium — wire-shape change. Feature-flag gating mitigates.

### 🟢 PR-2f — Cancellation API

**Branch:** `feat/v5.48-cancellation`

**Scope:**
- Agent: `POST /command/cancel?request_id=<id>` endpoint. Looks up
  ops.db row, sends cancel signal to running goroutine. For migrations,
  invokes `virsh domjobabort <vm>` rather than killing the child.
  For other actions, SIGTERM child → wait 5 s → SIGKILL.
- Server: `POST /api/command/cancel?request_id=<id>` proxies to the
  right agent (looks up host from command_log).
- Audit event `command.cancelled`.
- ops.db row marked `cancelled` with operator's reason.

**Acceptance criteria:**

  verify `virsh domjobabort` invoked, state cancelled.
- `TestCancel_SIGTERMsChild` — non-migration slow action; child PID
  receives SIGTERM, exits cleanly.
- `TestCancel_AlreadyTerminalNoOp` — cancel after success → 200,
  idempotent message.

**Docs (this is the phase-final PR for Phase 2):**
- `server/docs/changelog.md`: v5.48.0 entry covering the full Phase 2
  scope — durability, watchdog, async slow actions, cancellation.
- `server/docs/api.md`: document `POST /api/command/cancel`.
- `server/docs/troubleshooting.md`: "Cancelling a stuck action"

- New top-level page `server/docs/operations.md` — describing the

**Validation (post-merge, post-deploy v5.48.0):**

- Server: receives frames, persists to `command_log.last_progress`,

  fresh progress means agent is alive, no need to poll outcome.

**Acceptance criteria:**
