## How to use this doc

1. Re-read this file's "Next PR to ship" line at the top.
2. Open the matching PR section below.
3. Branch off `main` with the branch name listed.
4. Implement against the acceptance criteria.
5. Tests + lint must pass locally before push.
6. Open a PR via the Gitea API; wait for green CI; merge via API.
7. Update this file's "Next PR to ship" pointer + the row's status.
8. Stop if the next PR is marked **CHECKPOINT** — wait for operator.

## Status legend

## Definition of done (every PR, no exceptions)

Each PR is not "ready to merge" until **all four** are present:

1. **Code change** — implementation per the PR's scope.
2. **Tests** — at least the cases listed in acceptance criteria.
   Workflow files get `act`-driven dry-run validation; build
   pipelines get the smoke-test stage baked in (broken artifacts
   shouldn't be allowed to publish).
3. **Docs** — at minimum:
   - Update `server/docs/deployment.md` for any operator-visible
     change to install paths.
   - Update `server/docs/changelog.md` only on the **phase-final**
     PR (so the changelog reads as 3 coherent stories, not 13
     fragments).
   - Update this `v5.49-implementation-plan.md` — flip the row's
     status, advance the "Next PR to ship" pointer.
4. **Validation** — after merge, run the PR-specific smoke check
   listed below. Phase 0 PRs are mostly secrets / mirror plumbing
   so validation is "secret exists in Gitea" or "first manual
   workflow_dispatch succeeds."

If any of the four is missing or fails, the PR is not done.
Surface to operator instead of merging on partial completion.

**Branch:** `feat/v5.49-publish-gate`

**Scope:**

  with `output.publish` (true|false). Implements the trigger

  - prev=v5.48.7, cur=v5.48.8, no `[publish]` → false.

  - prev=v5.48.8, cur=v6.0.0 → true.
  - prev=v5.48.8, cur=v5.48.8 → false (no version change).

**Acceptance criteria:**
- Workflow runs to completion on every push to `main`.
- Outputs `publish=true|false` deterministically.
- Workflow visible in Gitea Actions UI; `workflow_dispatch`
  button present.

**Docs:** none operator-visible yet — gate is consumed by PR-1b.

**Validation:** push a commit that bumps VERSION patch without
`[publish]`; observe gate output `false`. Push a commit with
`[publish]`; observe `true`.

**Effort:** ~1.5 h.

**Risk:** low; gate is read-only — wrong output skips publish but
doesn't break anything.

### 🟢 PR-1b — Multi-arch Docker Hub publish workflow

**Branch:** `feat/v5.49-docker-publish-workflow`

**Scope:**
- New `.gitea/workflows/docker-publish.yml`:
  - `needs: [should-publish]; if: needs.should-publish.outputs.publish == 'true'`
  - `docker/setup-qemu-action` + `docker/setup-buildx-action`
  - `docker login` with `${{ secrets.DOCKERHUB_TOKEN }}`
  - `docker buildx build --platform linux/amd64,linux/arm64`
    with tags `:latest`, `:v$VERSION`, `:$MAJOR.$MINOR`, `:$MAJOR`
  - `docker push --all-tags thedon21/kvm-center`
  - `cosign sign --yes --key env://COSIGN_KEY thedon21/kvm-center:v$VERSION`
- Smoke-test stage between `push` and `cosign sign`:
  - `docker run --rm -d -p 18190:8190 thedon21/kvm-center:v$VERSION`
  - poll `https://localhost:18190/api/version` for up to 60 s
  - assert response matches `$VERSION`
  - `docker rm -f` on success or failure
  - on failure: `docker manifest rm thedon21/kvm-center:latest`
    (don't poison the rolling tag) and fail the workflow

**Acceptance criteria:**
- Workflow runs end-to-end on `workflow_dispatch` from a known-good
  commit (manually triggered for the first run).
- Resulting image is multi-arch: `docker manifest inspect` shows
  both `linux/amd64` and `linux/arm64` entries.
- `cosign verify --key docs/security/cosign.pub` returns success.
- Rolling tag `:latest` matches the version-tagged push.

**Docs:** none operator-visible at this PR; PR-1c is the README.

**Validation:** `docker pull thedon21/kvm-center:latest`,
`docker run -d -p 8190:8190 thedon21/kvm-center:latest`, hit
`/api/version`, see the expected version.

**Effort:** ~3 h.

**Risk:** medium — multi-arch buildx is the slowest path in CI.
Mitigated by smoke-test gate (broken artifact never tagged
`latest`).

### 🟢 PR-2a — Appliance build harness

**Branch:** `feat/v5.49-appliance-build-harness`

**Scope:**
- New `appliance/` top-level tree per spec §"Source tree layout".
- `appliance/build.sh` runs `virt-builder rocky-9.4 --output …`
  with the cloud-init customisations applied. Fully invocable
  locally (`make -C appliance build`) for development.
- `appliance/cloud-init/{user-data,meta-data}` seed installs
  `kvm-center` + `mongodb-server`, enables the systemd units,
  emits the firstboot service.
- `appliance/systemd/kvm-center-firstboot.service` generates
  admin password + self-signed cert on first boot, writes to
  `/etc/issue` + MOTD.
- `appliance/README.md` for developers (operator-facing copy
  comes in PR-2e).

**Acceptance criteria:**
- `make -C appliance build` produces a `kvm-center-appliance.qcow2`
  on a developer machine with virt-builder installed.
- Booting the qcow2 with `qemu-system-x86_64` produces a working
  kvm-center on `https://<vm-ip>:8190` within ~30 s.
- The first-boot password is visible at the libvirt console.

**Docs:** internal `appliance/README.md` only.

**Validation:** booted qcow2 responds to `/api/version` with the
embedded server version.

**Effort:** ~5 h (lots of cloud-init / systemd debugging on first
attempt).

**Risk:** medium; image-building tooling is finicky on first setup.

## Cross-cutting concerns (apply to every PR)

- **Branch-protection-friendly:** every PR opens against `main`
  via the Gitea PR API; squash-merge after green CI; no direct
  pushes. CI gates (`lint-test`, `webui-audit`, `gitleaks`,
  `e2e`) are mandatory.

  Phase 3 as v5.49.2. Phase-final PRs carry `[deploy]` in the
  squash-commit subject. Minor bump in v5.49.0 + v5.49.1
  auto-fires the publish workflow per PR-1a's gate.
- **Memory updates after each phase ships to prod:**
  - Update `project_active_work.md` to reflect the new prod
    version + the new install paths available.
  - Add `feedback_publish_pipeline.md` after v5.49.0 capturing
    operational notes (where Docker Hub creds live, how to
    re-publish manually via `workflow_dispatch`, cosign key
    rotation).
  - Update `MEMORY.md` index pointers.
- **Per-PR DoD (repeated for emphasis):** code + tests + docs +
  validation. If any of the four is missing, the PR is not done
  and should not be merged.
