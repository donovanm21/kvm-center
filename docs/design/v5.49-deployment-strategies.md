# v5.49 — public deployment strategies (Docker Hub + KVM appliance)

**Status:** approved, ready to implement after operator merges this PR
**Author:** autonomous review cycle, 2026-05-02
**Spec freeze:** locked decisions in §"Decisions log"

## Goals

Two new on-ramps for new operators trying kvm-center, alongside the
existing `install.sh` bare-metal install:

1. **Docker Hub image** — `thedon21/kvm-center:latest` (and version /
   minor / major channel tags) so a new user can `docker run` or paste
   a 15-line `docker-compose.yml` and have a working install in one
   minute. Auto-update story ships in the same readme.
2. **KVM appliance** — a prebuilt qcow2 + libvirt domain XML + a small
   helper script. Operator runs `virt-install --import` (or the
   virt-manager wizard) and gets kvm-center on first boot, no Linux
   distro selection / package install / TLS bootstrap to think about.

Both shipped under operator control: a development branch landing
`[deploy]` keeps the homelab-only deploy story untouched. Public
artifacts only get rebuilt when the operator opts in.

## Non-goals

- Helm chart / Kubernetes deployment (separate story; Phase 4 if ever).
- Multi-node clustered server (kvm-center is single-instance today;
  HA is out of scope).
- Auto-update of the appliance from inside the appliance VM
  (operator pulls a new qcow2 + re-imports for a clean upgrade in
  Phase 1; Phase 2 can revisit).
- AWS AMI / Azure VHD images (KVM-native is the only target for
  Strategy A).
- Push to GitHub Container Registry (ghcr.io) — Docker Hub is the
  documented default; ghcr can come as a follow-up if ergonomics
  warrant it.

## Decisions log

Locked 2026-05-02 with operator confirmation:

1. **Trigger model:** hybrid auto + override.
   - Default: minor / major version bumps (`5.48.x → 5.49.0`,
     `5.49.x → 6.0.0`) auto-publish.
   - Patch bumps (`5.48.7 → 5.48.8`) skip publish unless the
     commit subject carries `[publish]`.
   - `workflow_dispatch` button in Gitea Actions UI as a manual
     escape hatch (re-publish a missed release, backfill an
     appliance, force-push `latest` after a Hub outage).
2. **Appliance hosting:** **GitHub Releases** on
   `github.com/donovanm21/kvm-center`. Free, good UX, signature
   verification baked in, 2 GB per file (well under the qcow2
   target). Mirror push lands as a hard prerequisite — see §"Open
   prerequisites".
3. **Docker Hub multi-arch:** **amd64 + arm64.** Roughly doubles
   build time (~5 min → ~10 min) but lets M-series Mac users `docker
   run` to try the product without an emulator layer. ARM hypervisor
   adoption is small but non-zero and the cost is bounded.
4. **Quickstart format:** README front-loads a one-line `docker run`
   and a 15-line `docker-compose.yml`. No expanded prerequisites
   section; the operator wants to see kvm-center in five minutes.
5. **Appliance base OS:** Rocky Linux 9 minimal cloud image. Matches
   the hvnodes (familiar `dnf` / `firewalld`), broadly understood,
   well-supported `cloud-init`. Alpine would be smaller (~150 MB
   qcow2) but loses the "operator already knows this" benefit.
6. **Appliance stack form:** systemd unit running the Go binary +
   embedded MongoDB on the same VM. Single-VM, single-systemd-target,
   no Docker-inside-Docker. New operators want one thing to look at,
   not a Docker-in-VM matryoshka.
7. **Appliance first-boot config:** `cloud-init` generates the
   admin password + self-signed TLS cert at first boot, writes them
   to `/etc/issue` (visible at the libvirt console) AND emits an MOTD
   so SSH login also surfaces them. Same captive `/setup` wizard the
   product already ships catches the rest of the configuration.
8. **Signing:** Phase 1 ships **SHA256SUMS** for the qcow2 (signed
   by a maintainer-held key — operator's existing GPG key is fine).
   Docker Hub gets **cosign-signed manifests** (Sigstore). Both are
   well-trodden patterns and let downstream operators verify the
   provenance of artifacts they pulled.
9. **Docker Hub visibility: PRIVATE during development.** Repo is
   created private on Docker Hub at the start of Phase 0 and stays
   that way until the operator explicitly flips it public via the
   Hub UI — a single toggle, no CI changes required. The publish
   workflow (PR-1b) is identical for private vs public; only the
   operator-facing quickstart copy differs (private → operators
   must `docker login -u thedon21` first; public → anonymous
   `docker pull`). Quickstart docs land with a "private during
   development" banner that the Phase 3 polish PR removes when
   the operator gives the go-ahead. Cosign signing applies in
   both modes.
10. **Skip Phase checkpoints during execution.** Per operator
    direction (2026-05-02): the 🚧 CHECKPOINT badges in the
    implementation plan are markers for status reporting, NOT
    pause-and-ask gates. After each phase ships, I bundle the
    validation results into the next phase-final summary instead
    of pausing for green-light. Operator reviews the cumulative
    summary at the end. Stop-conditions in the plan still apply
    (CI flake >3, diff >2× estimate, real prod incident).

## Trigger logic detail

A new shared workflow `.gitea/workflows/should-publish.yml` evaluates
two conditions on every push to `main`:

```bash
# 1. Did VERSION change in this commit?
prev=$(git show HEAD~1:server/VERSION 2>/dev/null | tr -d '[:space:]')
cur=$(cat server/VERSION | tr -d '[:space:]')
if [ "$prev" = "$cur" ]; then echo "skip: no version change"; exit 0; fi

# 2. Is the bump minor or major (vs patch)?
prev_minor=$(echo "$prev" | sed 's/^v//' | cut -d. -f1-2)
cur_minor=$(echo "$cur" | sed 's/^v//' | cut -d. -f1-2)
if [ "$prev_minor" = "$cur_minor" ]; then
  # Patch bump — only publish if subject carries [publish]
  if ! git log -1 --format=%s HEAD | grep -q '\[publish\]'; then
    echo "skip: patch bump without [publish]"
    exit 0
  fi
fi
echo "publish: yes"
```

Output exposed as `outputs.publish` on the job; downstream
`docker-publish.yml` and `appliance-build.yml` workflows gate
`if: needs.gate.outputs.publish == 'true'`.

The `workflow_dispatch` path bypasses this gate entirely — operator
explicitly asked for it.

## Strategy A — KVM appliance

### Pipeline shape

```
operator commits VERSION 5.49.0 → push to main →
  gate: minor bump → publish=true →
  appliance-build.yml runs (privileged Gitea runner):
    1. virt-builder rocky-9.4 base + cloud-init seed-data
    2. dnf install kvm-center mongodb-server
    3. systemctl enable kvm-center mongod
    4. truncate /etc/machine-id (regenerated on first boot)
    5. sparsify (qemu-img convert) → kvm-center-appliance-v5.49.0.qcow2
    6. sha256sum > SHA256SUMS
    7. gpg --detach-sign SHA256SUMS
    8. boot test (cloud-localds + qemu) — wait for /api/version
       to respond, fail the workflow if it doesn't
    9. upload to GitHub Releases (gh release upload v5.49.0 …)
```

Estimated runtime: ~12–15 minutes per build. Acceptable on minor
releases (every few weeks). Patch releases skip unless `[publish]`.

### Operator import flow (documented)

```bash
# Download the artifact + signature
gh release download v5.49.0 --pattern 'kvm-center-appliance-*.qcow2*'
gh release download v5.49.0 --pattern 'SHA256SUMS*'

# Verify signature + integrity
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS

# Import + start
sudo cp kvm-center-appliance-v5.49.0.qcow2 /var/lib/libvirt/images/
sudo virt-install --name kvm-center --memory 2048 --vcpus 2 \
  --disk path=/var/lib/libvirt/images/kvm-center-appliance-v5.49.0.qcow2,bus=virtio \
  --import --os-variant rocky9 --network bridge=virbr0 --noautoconsole

# Watch the console for the auto-generated admin password + URL
sudo virsh console kvm-center
```

First boot completes in ~30 seconds; the operator sees:

```
============================================
 kvm-center is ready at https://10.0.0.123:8190
 admin password: K7p3nQv9x...
 (regenerate with: kvmctl admin reset-password)
============================================
```

### Source tree layout

```
appliance/
  README.md                  # operator-facing import guide
  Makefile                   # `make build` runs the local virt-builder pipeline
  build.sh                   # the orchestration script CI runs
  cloud-init/
    user-data                # systemd setup, kvm-center config, password gen
    meta-data
  rocky9-source.json         # virt-builder template + customisations
  systemd/

```

## Strategy B — Docker Hub

### Pipeline shape

```
operator commits VERSION 5.49.0 → push to main →
  gate: minor bump → publish=true →
  docker-publish.yml runs:
    1. docker buildx build --platform linux/amd64,linux/arm64 \
         -t thedon21/kvm-center:v5.49.0 \
         -t thedon21/kvm-center:5.49 \
         -t thedon21/kvm-center:5 \
         -t thedon21/kvm-center:latest .
    2. docker push --all-tags thedon21/kvm-center
    3. cosign sign --yes thedon21/kvm-center:v5.49.0
    4. smoke-test: docker run --rm -d -p 18190:8190 thedon21/kvm-center:v5.49.0;
       wait for /api/version; assert response matches v5.49.0;
       docker rm -f the container.
    5. failure path: untag `latest` (don't poison consumers); workflow fails.
```

Estimated runtime: ~10 minutes (multi-arch buildx is the hot
spot). Acceptable for minor releases; manual `workflow_dispatch`
re-runs are similarly bounded.

### Operator quickstart (docker run, single line)

```bash
docker run -d --name kvm-center -p 8190:8190 \
  -v kvm-center-data:/data \
  -e KVM_CENTER_PUBLIC_URL=https://localhost:8190 \
  thedon21/kvm-center:latest
```

Open `https://localhost:8190`, accept the self-signed cert, walk the
captive setup wizard. ~60 seconds end-to-end.

### Operator quickstart (docker-compose, with Mongo)

`docker-compose.yml` (15 lines, README front-and-centre):

```yaml
services:
  mongo:
    image: mongo:7
    volumes: [mongo-data:/data/db]
    environment:
      MONGO_INITDB_ROOT_USERNAME: root
      MONGO_INITDB_ROOT_PASSWORD: ${MONGO_PASSWORD:?set MONGO_PASSWORD}
  server:
    image: thedon21/kvm-center:latest
    depends_on: [mongo]
    ports: ["8190:8190"]
    environment:
      KVM_CENTER_MONGO_URL: mongodb://root:${MONGO_PASSWORD}@mongo:27017
      KVM_CENTER_PUBLIC_URL: https://localhost:8190
    volumes: [kvm-center-data:/data]
volumes:
  mongo-data:
  kvm-center-data:
```

Update story: `docker compose pull && docker compose up -d` —
documented inline. For operators who want push-button auto-update,
a Watchtower label snippet is also in the README:

```yaml
labels:
  com.centurylinklabs.watchtower.enable: "true"
```

### Multi-arch buildx caveats

- The agent binary is built per-architecture inside the Docker image
  build (already cross-compiles cleanly via Go). No extra CI work.
- The SPA bundle is architecture-agnostic; emitted once during the
  image build.
- Buildx requires a privileged runner OR a remote builder. The
  Gitea runner host has Docker installed; we'll set up a buildx
  builder pointing at the same daemon.

## Smoke tests (both strategies)

Critical to bake in: a published-but-broken artifact is much worse
than a missed publish. The pre-publish test gate runs:

- **Docker Hub:** `docker run -d -p 18190:8190 IMAGE:NEW`,
  wait for `/api/version` to respond with the expected version
  string within 60 s, then container-rm. If it fails, untag
  `latest` and fail the workflow. The version-tagged push (e.g.
  `:v5.49.0`) stays visible in case the operator wants to debug,
  but `latest` doesn't move.
- **Appliance:** `cloud-localds` a minimal seed disk, boot the
  qcow2 with qemu-system-x86_64, port-forward 8190 → host:18190,
  poll `/api/version` for up to 90 s. Same fail-the-workflow,
  don't-publish-the-artifact contract.

## Open prerequisites (blockers)

1. **GitHub mirror push must land first.** Releases live on
   `github.com/donovanm21/kvm-center`. The mirror is currently at
   v5.46.6 (per `feedback_github_mirror.md` — every push must
   filter-repo through `/tmp` to scrub internal IPs and committed
   binaries). PR-0a in the implementation plan handles this.
2. **GPG key for SHA256SUMS signing.** Operator's existing key is
   fine; needs to be added as a Gitea Actions secret
   (`APPLIANCE_SIGNING_KEY`). PR-0b does this.
3. **Docker Hub credentials.** Operator creates a token scoped to
   `thedon21/kvm-center` push only (not full account access).
   Stored as Gitea Actions secret `DOCKERHUB_TOKEN`. PR-0c.
4. **Cosign key for image signing.** Generated fresh; public key
   committed to `docs/security/cosign.pub` so consumers can
   verify. Private key as Gitea secret `COSIGN_KEY`. PR-0d.

These four are mechanical setup; they collectively unblock
everything in Phase 1 + 2.

## Failure modes

| Scenario | Detect | Recover |
|---|---|---|
| Docker Hub push fails mid-arch | buildx exit code | retry workflow_dispatch; previous tags untouched |
| Cosign signature fails | step exit code | publish workflow fails; image stays unverified — operator can re-run cosign manually if needed |
| qcow2 boot smoke test fails | poll timeout | workflow fails; no GitHub Release uploaded; operator inspects logs |
| Operator pushes a patch with `[publish]` and gate accepts | n/a — by design | the override is intentional |
| Operator forgets `[publish]` on critical patch | nothing publishes | trigger workflow_dispatch manually; same outcome as if `[publish]` had been there |
| Auto-publish fires on a buggy minor release | smoke test catches obvious; subtle bugs ship | revert via patch + `[publish]`; cosign verifies operators downstream got the right thing |
| GitHub mirror push lags | `gh release upload` fails because the tag doesn't exist on github | mirror push must be in the publish workflow's preflight (it is — see PR-3a in the plan) |
